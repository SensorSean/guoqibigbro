## 1. 顶部导航响应式方案（推荐：不加汉堡菜单）

### 1.1 为什么不需要汉堡 / 下拉
合并后 tab 数 6→5，总宽约 435px（实测：数据源≈84 + 字段映射≈84 + 预览与执行≈97 + 使用说明≈84 + 关于≈70 + 间距16）。
窗口最小 800px 下：48(padding) + 130(logo) + 16(gap) + 435(tabs) ≈ **629px < 800px** → **5 个 tab 在最小窗口即可完整放下**。
因此**不引入汉堡菜单**（会牺牲直接可达性、增加 JS 复杂度），仅做「防压缩 + 防换行 + 极端兜底横向滚动」三件事即可。

### 1.2 必须修复的 4 处 CSS（style.css）
**删除** L20–31 的 `.app-author` 整块。
**替换** L66–82 的 `.topbar / .logo / .subtitle / .nav-tabs / .nav-tab`：

## 2. 合并「预览确认」+「执行结果」→ 单页（推荐：宽屏左右，窄屏上下）

### 2.1 信息架构（合并后 5 页）
```
0 数据源      （不变）
1 字段映射    （不变，「确认并预览 →」仍 switchPage(2)）
2 预览与执行  ← 原「预览确认」+「执行结果」合并
3 使用说明    （原 index 4）
4 关于        （原 index 5，新增更新日志）
```
> 字段映射页「确认并预览 →」(`index.html` L86 `switchPage(2)`) **保持不动**，目标页即合并页。

### 2.2 推荐布局理由
- 预览表是**宽表**（目标字段 × 多行），适合横向铺满 → 占主区。
- 执行控件（进度环 + 阶段文案 + 按钮 + 日志 + 打开结果 / 新建任务）**纵向信息密集** → 适合侧栏。
- 合并后单页完成「核对 → 执行 → 看结果」，路径更短，且 tab 减 1 缓解导航拥挤。
- 复用既有 `.preview-table` / `.progress-ring-wrap` / `.log-item` / `.pill` 组件，**零新视觉元素**。

### 2.3 宽屏（≥980px）：左预览 + 右固定 320px 侧栏

## 8. 最小宽度结论
**维持 `main.py` 现有 `min_size=(800, 600)` 即可**，无需调整。理由：
- 实测 800px 下 5 个 tab + logo 约 629px，有余量；
- 错位根因是 flex 压缩/换行，不是窗口过小，靠 §1.2 的 CSS 修复根治；
- 额外设更小最小值只会重新引入错位风险，故不建议。
