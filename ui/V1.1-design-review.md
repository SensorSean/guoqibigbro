# 国企大表哥 V1.1 — 设计审查与设计调整方案

> Designer-20 · 基于真实 v4 代码（`index.html` / `style.css` / `app.js`）+ 用户反馈 + 现有 3 份 mockup 的合并结论

---

## 0. 结论速览（按优先级）

| 优先级 | 事项 | 一句话结论 |
|--------|------|-----------|
| **P0** | 顶部导航错位 | 根因 = 缺 `flex-wrap` 守卫 + 缺 `min-width`/`flex-shrink` 约束 + **完全没有响应式断点** + 6 个 tab 在窄屏无法降级。修复只需加 CSS 守卫与 2 个断点。 |
| **P0** | 删除「软件作者：LuoLei」 | 删 `app-author` 节点与样式，并**用 `V1.1` 版本药丸顶替其位置**（平衡顶部、呼应更新日志需求）。作者信息已在「关于」页，不丢失。 |
| **P1** | 预览确认 + 执行结果合并 | 采用**上下分区**（可折叠预览 → 进度环 → 吸底操作栏），不用左右分区。理由：用户流程是时序型的（核对→确认→看进度→打开），且表格需要整宽。 |
| **P2** | 更新日志模块 | 放在**「关于」页**（与版本信息同域），**不要**放「使用说明」页；同时把「关于」页 V1.0 → V1.1。 |

## 1. 顶部导航窄窗口错位的根因

对照 `style.css` 现状：

```css
.topbar { height:56px; display:flex; align-items:center; padding:0 24px; gap:16px;
          position:fixed; top:0; left:0; right:0; }       /* ① 没有 flex-wrap */
.logo   { ... display:flex; align-items:center; gap:8px; } /* ② 没有 flex:0 0 auto / min-width */
.nav-tabs { display:flex; gap:4px; margin-left:auto; }     /* ③ 没有 overflow-x / min-width:0 */
.nav-tab  { padding:8px 16px; ... white-space:nowrap; }    /* ④ 子项 nowrap */
/* ❌ 全局没有 @media 断点 */
```

**根因拆解（按贡献度）：**

1. **完全缺失响应式断点（最关键）。** `style.css` 里没有任何 `@media` 规则。窗口一窄，整条导航只能靠 flex 强行挤压，没有任何回收空间的手段。
2. **`flex` 子项无收缩守卫。** `.logo` 默认 `flex-shrink:1`，但内部 `logo-img(32px) + 国企大表哥(18px) + subtitle(11px,约22字) + app-author(11px)` 都是 `white-space:nowrap`。logo 盒子被压到内容宽度以下时，文字溢出/与右侧 tab 重叠 → 视觉「错位」。
3. **`.nav-tabs` 用 `margin-left:auto` 推到最右，且整行 `nowrap`。** 6 个 pill（每个约 56px + 4px gap ≈ 360px）加上 logo 簇（含 app-author 约 450px），合计约 820px 起点宽度。窗口 < 820px 时无任何降级路径，直接挤压。
4. **`app-author` 标签本身加剧了问题。** 它给 logo 簇额外增加约 110px 横向占用，是窄屏最先撑爆的元凶之一（删除它本身就是修复的一部分）。
5. 桌面工具（pywebview）场景下，没有汉堡菜单是 OK 的——**横向滚动 tab + 隐藏副标题** 比折叠成菜单更符合桌面交互习惯。

## 2. 删除 app-author 后，顶部空间是否需要再调整？

**结论：需要，但只需低风险补一个 `V1.1` 版本药丸，不必大改。**

- 删除 `app-author` 后，logo 簇从「图 + 名 + 副标题 + 作者药丸」变回「图 + 名 + 副标题」，剩余约 110px 空隙。
- 三种处理方式对比：

  | 方案 | 评价 |
  |------|------|
  | A. 什么都不加（logo 自然变短） | 可用，但浪费了一次"传达版本"的机会，且左侧留白略空 |
  | **B. 用 `V1.1` 版本药丸顶替** ✅ | **推荐**。复用被删标签的同一水平槽位，视觉重量一致；同时与本次"更新日志"需求形成呼应 |
  | C. 把副标题加长/放大 | 不推荐，副标题是装饰性英文，加长反而更挤 |

- 作者信息**不丢失**：「关于」页已有 `开发人员：LuoLei`（index.html 第 227 行），首页删除后信息仍在规范位置。

## 3. 合并页信息架构：上下分区 vs 左右分区

用户流程：**核对（预览）→ 确认执行 → 看进度 → 打开结果**，是**时序型、阶段互斥**的，不是并行对比。

| 维度 | 上下分区（推荐） | 左右分区 |
|------|----------------|----------|
| 契合时序流程 | ✅ 顺流而下，每阶段独占视区 | ❌ 暗示同时查看，违背流程 |
| 表格可读性 | ✅ 预览表可占满整宽（max-width 900px） | ❌ 左栏被压窄，宽表换行/横向滚 |
| 进度/日志 | ✅ 居中或整宽，清晰 | ❌ 右栏变窄列，日志拥挤 |
| 实现复杂度 | 低（折叠面板 + 吸底栏） | 高（需 Grid 分栏 + 各自滚动） |

**推荐结构（上下 + 可折叠预览 + 吸底操作栏）：**

```
┌─────────────────────────────────────┐
│ 执行  [预览表格 ▾]            (页头) │
├─────────────────────────────────────┤
│ [可折叠] 预览表（前5行）              │
│                        ✅ 确认执行  │  ← 预览面板底部右对齐
├─────────────────────────────────────┤
│            ◯ 进度环 100%              │  ← 点确认后预览自动收起
│         📋 日志列表                  │
│    📂 打开结果文件   🔄 新建任务      │  ← 完成后出现的吸底操作栏
└─────────────────────────────────────┘
```

- "确认执行"按钮只保留**一份**，放在预览面板右下角；点它后预览自动折叠，进度环出现（即原来的「开始执行」按钮可删除，避免双触发）。
- 进度到达 100% 后展示日志 + 吸底操作栏（打开结果 / 新建任务）。
- **保留所有原 id**（`preview-table` / `progress-circle` / `log-list` / `export-btn` / `reset-btn`），`app.js` 仅微调显隐与 `confirmAndExecute` 逻辑，无需重写。

> 现有 mockup 中 `v1.1-designer16.html` 与 `preview-v1.1.html` 均采用了此上下结构，方向正确，本方案采纳并细化交互次序。

## 5. 更新日志模块放哪？

**结论：放「关于」页，不放「使用说明」页。**

- 「使用说明」语义 = *怎么用*；「更新日志」语义 = *改了什么*。混放会削弱两页的信息架构清晰度。
- 「关于」页本就承载版本信息（V1.0 徽标 / 技术栈 / 发布日期），是更新日志的天然归属。
- 建议：「关于」页新增**可折叠「📝 更新日志」模块**，且把页面内 `V1.0` 全部升为 `V1.1`。
- 「使用说明」页**仅**在标题处加一个小小的 `V1.1` 版本药丸做上下文提示即可，不必放完整日志。
- 三步说明可顺带由 5 步精简为 4 步（"预览确认"与"执行结果"合并为一步"预览并执行"），与页面合并保持一致。
